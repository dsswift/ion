# ADR-034: Principal Isolation and Tenancy

## Status

Accepted. Builds on [ADR-033](033-ion-studio-server-and-environments.md).

## Context

ADR-033 made one server plus one engine (an Environment) serve several signed-in people at once. That closed the process-topology gap but left an isolation gap: a per-session `SessionPrincipal` existed on the wire, but nothing yet stopped one principal's tab, conversation, tool call, or git commit from being visible to — or attributed to — another. Validating `ion-beta`'s first multi-tenant instances against real Entra principals surfaced four concrete leaks (tab rows, mirror-sync channels, action dispatch, and an unresolved-ownership fail-open) and four feature gaps (storage never partitioned on disk, tool policy identical for every principal, git commits all attributed to one shared identity, and a shared-tenancy escape hatch that didn't exist at all).

This ADR is the isolation layer ADR-033's principal made possible but did not itself build.

## Decision

**Every read and write that names a tab, a conversation, or a file on disk is gated by the connection's principal**, not merely labeled by it. Four fail-closed checks cover the whole studio-wire surface: `tabVisibleTo` (snapshot/hello), `filterBySubject` (the remote/iOS tab projection), the per-principal mirror-sync projector, and the `studio_action`/`studio_event` ownership check. A tab or conversation with no recorded `principalSubject` (a pre-partitioning legacy record) is visible to everyone in single-tenant mode and to no one once any principal partitioning is active — an unresolved owner fails closed, never open.

**Conversation storage partitions by principal on disk** (`engine/internal/conversation/partition.go`) when `engine.json`'s `security.principalPartitioning.enabled` is true: each principal's conversations live under `<dataDir>/principals/<PrincipalDir(subject)>/conversations/`, a sibling of the flat `<dataDir>/conversations/` root every principal's session could otherwise enumerate — the flat root remains the home for unattributed sessions only, and is never migrated. Partitioning carries an enforcement level — `strict` (the default: no cross-principal access at all), `read-only` (cross-principal reads allowed, writes confined to your own partition), or `none` (a storage-layout convention only, logged at WARN on every boot since it is never a silent downgrade) — that governs what a session may do to a conversation it doesn't own when directly addressed by ID. `get_host_info` publishes `principalPartitioning: {enabled, enforcement, root}` so a harness can detect the mode without guessing from file layout, and `start_session`'s result and the identity-changed hook payload both carry `storageRoot` — the session's own partition directory — so a harness can locate its data root without re-deriving the partitioning rule itself (see the cos2 harness's `StorageRoot`-first resolution, below).

**Tool policy is per-principal, layered on the global policy, not a replacement for it.** An enterprise sealed config's `security.toolRestrictions.principals[]` matches a principal by subject, provider, or claim and layers allow/deny rules on top of the existing global allow/deny lists — the global deny always wins first, even over a principal-specific allow; among matching per-principal rules, deny wins and allow lists intersect. A refused call emits the `enforcement.tool_blocked` telemetry event naming the tool, the principal, and which rule fired, so a refusal is auditable rather than a silent no-op. **The execution boundary is a separate, lower-level backstop** (`engine/internal/principalboundary`): for the structured-path tools (Read/Write/Edit/Glob/Grep) and as an immediate non-adversarial check for Bash, it refuses a path outside the session's own partition directly at the tool call, independent of whether the policy layer above ever considered it — the real adversarial boundary for a shell is the OS-level sandbox (Seatbelt/bwrap, `security.sandbox`), which partitioning wires with a deny-read on every other principal's partition and an allow-read exception carved back for the session's own.

**Git identity resolves per principal**, not per server. `server.json`'s `git` block supports three credential sources in precedence order — admin-managed credentials (`git.credentials[]`, secret-store-backed SSH keys or tokens scoped to a subject and host), an OAuth exchange (Azure DevOps on-behalf-of, GitLab, or a GitHub App), and a user-supplied credential entered in Studio Settings last — and author identity (name + email) resolves independently from the session's own principal. The engine stamps `GIT_AUTHOR_*`/`GIT_COMMITTER_*` from the resolved author identity; the server separately injects the resolved credential's `GIT_SSH_COMMAND` (SSH) or `GIT_ASKPASS`/`GIT_TERMINAL_PROMPT` (HTTPS token) into the session's tool environment — so a commit's authorship AND the credential it pushed with both match who actually asked for it, never the server's own service identity.

**Tenancy has an explicit mode, not just an implicit consequence of partitioning.** `server.json`'s `tenancy.mode` is `'isolated'` (default) or `'shared'`. Isolated mode is everything above: every visibility and ownership gate enforces per-principal separation. Shared mode is the deliberate escape hatch — every gate above short-circuits to "visible to everyone," for a genuinely single-team, no-secrets-between-us deployment that wants one shared view of every tab. Presence (who is connected, which tab they're focused on, which tab they're driving) is orthogonal to tenancy mode and always shows every connection: presence is about who else is here, which isolated mode is not designed to hide, unlike the tab contents themselves. Shared mode is refused at boot when the engine's own `principalPartitioning.enabled` is also true — the two features contradict each other (partitioned storage with a UI that shows everyone everything is a leak, not a feature), and `/readyz` reports the conflict rather than starting in a state neither mode intended.

**Settings are classified personal or environment, and environment settings can be locked.** `@ion/shared/settings-classification` tags every settings-dialog category — models/tiers, default provider, AI workflow instructions, git operation policy, MCP servers, and enterprise-relevant automation are `environment` (shared configuration, not this device's own preference); appearance, tabs, notifications, and a person's own git identity are `personal`. Every non-local connection has every `environment` group hidden regardless of enterprise config — a remote connection is never the machine's own owner — and the local desktop can be additionally narrowed by an enterprise sealed config naming groups in `hiddenSettingsGroups`. A mutation whose group is hidden for the caller is refused server-side with `{code:'settings_locked'}` before it reaches the underlying action, so the lock is enforced at the API boundary, not only hidden in the UI a determined client could bypass.

## Consequences

- A conversation, a tab, and a tool policy all now have exactly one question to answer before use: does this connection's principal own it (or is the tenant explicitly shared)? Every new studio-wire surface that names a tab or conversation must answer that question, or it is a new leak by omission.
- Storage partitioning is additive and off by default: an existing single-tenant install with `principalPartitioning.enabled` unset (or false) sees a byte-identical `StorageRoot` (empty) and byte-identical file layout. The empty-means-unchanged contract is load-bearing for every consumer, including third-party harnesses (see the cos2 harness update, which resolves its own data root from `StorageRoot` when present and falls back to its historical `COS_DATA_ROOT`/`CLOUDOPS_HOME` derivation otherwise).
- Presence and tenancy mode are independent axes on purpose: an operator can run shared tenancy (single team, no isolation needed) while still seeing who's driving a tab, or isolated tenancy with presence limited to what each principal's own connection reports about itself.
- Settings classification is a registry, not a per-call judgment: adding a new settings-dialog category requires classifying it in `settings-classification.ts` or a completeness test fails, so a new category can never silently default to "always visible" by omission.

## Rejected

- **Hiding presence in isolated mode**: rejected. Presence answers "who else is connected," which is a materially different question from "what is in this tab" — collapsing the two would mean isolated-mode operators can't tell whether anyone else is even in the environment, which is worse for the collaboration cases isolated mode is still meant to support (shared engine, private conversations).
- **A single global tool-policy list with no per-principal override**: rejected because an enterprise sealed config legitimately wants different tool access for different roles on the same shared engine (a read-only reviewer principal vs. an admin principal); one global list can't express that.
- **Classifying settings by desktop-vs-iOS instead of personal-vs-environment**: rejected because the same category (AI & Models) needs the same hide/lock behavior on every client — the classification is about who the setting belongs to, not which client renders it.
