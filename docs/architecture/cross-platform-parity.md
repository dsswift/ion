# Cross-Platform Parity

> **Scope of this table.** The parity rules below apply when a feature *exists* on both desktop and iOS today and a change to one demands a change to the other. They do not require every new engine feature to ship simultaneously on desktop and iOS — engine surface ships ahead of reference implementations by design (see [Engine Consumers](engine-consumers.md)). Use this section as a sync checklist for already-paired surfaces, not as a coverage mandate for new ones.

Desktop and iOS are co-equal clients. When a desktop change touches a feature that also exists on iOS, **you must assess the iOS impact before considering the work complete.**

## Checklist for every desktop UI/state change

1. **Does this feature exist on iOS?** Check `ios/IonRemote/Views/` and `ios/IonRemote/ViewModels/` for the iOS counterpart.
2. **If yes:** update the iOS side in the same PR, or document why it's deferred.
3. **If the feature can't translate to iOS** (no physical space, no interaction model): document the trade-off. Consider an alternate iOS-appropriate rendering before deciding to skip.
4. **If state flows through the snapshot** (`server/src/remote/snapshot-polling.ts`, published to thin clients by `server/src/thin-view/thin-sync.ts`): check whether the snapshot projection needs updating. The snapshot is the bridge — iOS can only see what the snapshot sends. Settled conversations are the one exception: they left the snapshot and ride `desktop_settled_tabs` on their own hash gate (`server/src/thin-view/thin-settled.ts`).

## Common parity surfaces

| Desktop | iOS counterpart | Sync path |
|---------|----------------|-----------|
| Status dot (InboxRow, StatusDot) | Inbox row dot (TabRowView.statusInfo) | `snapshot.ts` → `RemoteTabState.status` |
| Engine instance bar (StatusBarEngineState) | Engine instance bar (EngineInstanceBar) | `snapshot.ts` → `RemoteTabState.conversationInstances`. The model-fallback indicator is derived via `resolveTabModelFallback` (`conversation-status.ts`). |
| Permission denials / waiting state | Permission queue / waiting state | `snapshot.ts` promotes denials into `permissionQueue`; per-instance `waitingState` on `conversationInstances` |
| Thinking indicator / interrupt button | Activity indicator / interrupt button | `desktop_tab_status`; iOS derives its running tools from the transcript rows' `toolStatus`, never from separate events. |
| Conversation View (rows from `studio_body`, kept live by the server store's own reducer over `ion:normalized-event`) | Conversation View (`SessionViewModel+Transcript.swift`) | The server store's rows are the one transcript. A thin client asks `studio_body_request` for a snapshot and applies `desktop_transcript_patch` events (`server/src/transcript/transcript-publisher.ts`). A revision gap re-fetches the snapshot. iOS builds no rows of its own; its only local row is the pending bubble of a prompt it sent, dropped when the server's row with the same `clientMsgId` arrives. See [ADR-036](adr/036-thin-clients-render-the-server-transcript.md). |
| Agent panel transcript (`useDispatchTranscript`, `mergeDispatchTranscript`) | Dispatch transcript (`SessionViewModel+DispatchTranscripts.swift`) | The server computes Studio's own rows for a dispatch (`server/src/transcript/dispatch-transcript-publisher.ts`) and streams them the same way, keyed `dispatch:<conversationId>:<dispatchId>`. A tab reads only the dispatches it owns. |
| Conversation row menu (InboxRowMenu) | Tab row context menu (TabRowContextMenu) | Actions operate on `RemoteTabState` fields; session identity via `snapshot.ts` → `RemoteTabState.conversationId` for all conversations. For extension-loaded tabs, per-instance session IDs are available in `conversationInstances[i].conversationIds` (historical) and `StatusFields.sessionId` (live). |
| Settings dialog (SettingsDialog: This Device / You / Servers, each server opening into its pages) | Settings (This iPhone / You / Servers, each paired server opening into the same pages) | `projectable-settings.ts` → `desktop_settings_snapshot` event. The phone renders a server's pages from the snapshot's `pages` and places each projected row in the section its schema entry names; every section also shows its admin screen, if it has one, above its projected rows. The snapshot is built PER CONNECTION (`buildDesktopSettingsSnapshot`): the values are that person's, each schema entry carries its `scope` from the settings registry, and `canManageEnvironment` says whether the connection holds `admin`. iOS shows an Environment entry read-only when it is false. Each schema entry also names the `page` and `section` Studio shows it on, and the snapshot's `pages` lists Studio's pages in order, so the phone uses the same page names and order (`packages/shared/src/settings-taxonomy.ts`, which Studio's `settings-catalog.ts` is built from). A phone write (`settings.setProjectable`) routes by the same registry as `settings.save`: Environment keys to the server document with `admin`, everything else to the caller's overlay. Entries whose scope is `personal` or `device` are the phone's own (`PersonalPreferencesStore`): stored on the phone, listed once under "This iPhone" rather than in a server group, and never written to a server, which refuses them (`wrong_scope`). The ones a server consumes are declared with `desktop_declare_preferences`. Studio's Settings dialog has the same split. A server's pages work whether or not the phone chats on that server: the phone's per-server admin session uses the live connection for the server it chats on and opens a connection of its own to any other paired server while its pages are on screen, keeping that connection's own settings snapshot and scopes. iOS group IDs **must** match `PROJECTABLE_GROUP_ORDER` (exported from `projectable-settings.ts`); renaming a group requires updating `PROJECTABLE_GROUP_LABELS` in that same file and the test in `server/src/__tests__/projectable-settings.test.ts`. Adding a new user-editable setting requires a registry entry (`packages/shared/src/settings-registry.ts`) and, when a phone should edit it, a parallel entry in `PROJECTABLE_SETTINGS_DATA`. |
| Model picker and context ring (StatusBarModelPicker, StatusBarContextIndicator, StatusDrawer) | Model picker and context strip (ConversationStatusBar, ConversationContextStrip, StatusDrawerView) | The server resolves the model a conversation runs on (`server/src/model-resolution.ts`, owner's Account settings) and publishes it: `liveResolvedModel` on `studio:tabs-sync`, `resolvedModels` on the welcome snapshot, `RemoteTabState.resolvedModel` and `conversationInstances[i].resolvedModel` for thin clients. No client falls back to a default model of its own. |
| Model fallback indicator (EngineStatusBar per-instance ⚠) | Model fallback indicator (EngineInstanceBar per-instance ⚠) | `snapshot.ts` → `RemoteTabState.conversationInstances[i].modelFallback`. Desktop populates `engineModelFallbacks` from the `engine_model_fallback` event; the snapshot poller projects each entry onto the corresponding `conversationInstances[i]` and iOS reads it from the snapshot. Cleared on the next idle transition (per-instance). |
| Worktrees list (git panel WorktreesSection) | Worktrees & Bench screen (WorktreeListView) + new-tab sheet rows | `desktop_worktree_state` → `RemoteWorktreeState.worktrees`. The desktop computes dirty/unlanded/needsSync; clients render, never derive. |
| Integration bench (git panel IntegrationSection) | Bench sections in WorktreeListView | `desktop_worktree_state` → `RemoteWorktreeState.benches`. Pins, staleness, and conflict attribution are all main-process values. |
| Worktree lifecycle verbs (land / sync / retire) | Tab-row context menu + worktree row swipe actions | `desktop_worktree_*` / `desktop_bench_*` commands; results ride `desktop_worktree_op_result` so a refusal reads differently from a failure. |
| Base-moved indicator (WorktreeRow) | Tab row indicator (TabRowView) | `RemoteWorktree.needsSync`. Only set when a sync would actually change the worktree — never for a no-op. |
| Inbox view (Studio InboxSidebar / classifier) | Inbox view (TabListView Inbox mode, InboxRowView) | `snapshot.ts` → `RemoteTabState.inboxState`/`unread`/`snoozedUntil`/`settledAt`/`wokeAt`/`lastActivityAt`/`idleSince`. The desktop computes the classification (shared/inbox-classify.ts); clients render, never derive. Inbox actions ride `desktop_tab_settle`/`_unsettle`/`_snooze`/`_unsnooze`/`_mark_unread`. View mode (tabs vs inbox) is per-device on both platforms, never synced. |
| Guided Questions wizard (Studio QuestionsSurface / QuestionsWizard) | Questions card + full-screen wizard (QuestionsCardView, QuestionsWizardView) | Desktop main's QuestionsCoordinator is the ONE workflow owner. iOS first paint rides `snapshot.ts` → `RemoteTabState.questions`; live updates ride `desktop_questions_state`; mutations ride revisioned `desktop_questions_patch`/`_action` (compare-and-set by revision, stale rolls back) and `desktop_questions_refresh` re-sends targeted state. The display-hint resolver (pills vs radio/checkbox) is one deterministic rule pinned by unit tests on both platforms (`questions-schema.test.ts` / `QuestionsWireTests`). |
| File links in message text: ⌘-click opens, ⌥⌘-click opens natively (`open-file-link.ts`) | File links in message text: tap opens, long-press menu offers Preview, Download, Copy Path (`LinkableText`) | `fs.resolveLink` resolves the path on the server that owns the conversation (its home for `~/`, the working directory for a relative path). Both clients show text in their own viewer. Anything else comes over as bytes through `fs.readFileData` (up to `MAX_FILE_DATA_BYTES`): the desktop opens a local copy or saves it through a dialog that starts in Downloads, and the phone shows it in Quick Look or saves it to Files. |
| Theme registry + picker (AppearanceCategory) | Theme picker (SettingsAppearanceView) | Built-in themes are compiled into both clients and pinned identical by the parity fixture (`assets/theme-parity.json`, asserted by `theme-parity.test.ts` on desktop and `ThemeParityTests.swift` on iOS) — a shared-theme palette edit must update the fixture and the Swift theme in the same change. Custom theme packs sync their iOS components via `desktop_theme_manifest` (sendSync + on pack-set change) with lazy asset fetch (`desktop_request_theme_asset`); enterprise lock rides `desktop_settings_snapshot.themePolicy`. Theme selection is per-device (never synced). Authoring guide: `docs/design/theme-packs.md`. |
| Environment page, Overview and Projects (server facts, restart, update, purge; project list, add, clone, trust, setup, relocate, remove, clone jobs) | Overview and Projects pages of a server in Settings → Servers | Every verb is an `environment.*` studio_action and every progress signal an environment-scoped channel (`ion:project-job`, `ion:projects-changed`), delivered to both views. The phone calls the same actions; each one it calls is listed with its scope in `packages/shared/src/studio-wire/phone-actions.json` (see [Studio wire § Phone actions](../protocol/studio-wire.md#phone-actions)). A phone refuses an action its pairing's scopes do not allow before sending it, and says which scope is missing. The phone adds a project from a folder on the server, a git URL, or another paired server's project. |
| Git access page (credentials, add, sign-in, test access, commit author) | Git access page of a server | `gitIdentity.*` for credentials (list, mint an SSH key, paste a key, store a token, remove, start a git host's OAuth sign-in), `environment.git.test` and `environment.git.hostKeys` for access, `environment.git.author.get`/`.set` for the commit author. The same actions on both clients: the phone enters secrets as the desktop does. `gitIdentity.authorize` answers `authorizationUrl`, which the phone opens itself. |
| Providers & models page (providers with API keys and sign-in, default models, model tiers, default provider) | Providers & models page of a server | `model.*` and `provider.*` actions, with `ion:model-tiers-updated`, `ion:default-provider-updated`, and `ion:provider-login-event` delivered to both views; a phone re-reads the tiers and the default provider on those signals. Sign-in differs by where the client runs: a delegated-CLI sign-in whose flow needs a browser on the host is refused off the host (`HOST_ONLY_LOGIN_REFUSAL`), so the phone offers only paste-code and device-code sign-ins and API keys. Google off the host is a paste-back sign-in (`oauth.start` → `auth.completeSignIn`). |
| Integrations page, MCP servers (add, remove, sign in, sign out) | MCP servers section of a server's Integrations page | `mcp.*` actions; `ion:mcp-servers-changed` reaches both views. The desktop's sign-in finishes on the engine's loopback listener on the host. The phone calls `mcp.login` with its own `redirectUri`, opens the returned page in an in-app browser sheet, and hands the address it returns to back through `auth.completeSignIn`; when the provider will not return to the app, the person pastes the address the browser landed on. |
| Integrations page, Automations (list, editor, enable per project, duplicate, delete, activity) | Automations section of a server's Integrations page | `automation.*` actions. The phone re-reads the listing after each change it makes; it has no live automation channel. The phone's copy of the automation catalog (triggers, conditions, actions) is pinned against the server's by a shared fixture (`packages/shared/src/__tests__/fixtures/automation-catalog.json`). |
| Integrations page, Enterprise sign-in (Entra) | Enterprise sign-in section of a server's Integrations page | `entra.identity`, `entra.signIn`, `entra.signOut`. The desktop signs in through the browser on the host. The phone asks `entra.signIn` for the device flow (`{flow: 'device'}`) and shows the code and the page to enter it at. |
| Access & pairing page (paired devices, pair a phone, pairing links, discovery, the server's name on phones, relay setup) | Access & pairing page of a server | `auth.listClients` (each device says whether it is connected now), `auth.revokeClient`, `auth.createPairingLink`, `environment.discovery.*`, `remote.setDisplay`, and the relay actions (`remote.testRelay`, `remote.discoverRelays`, `remote.relayAuthConfig`, all `admin` from any transport). `ion:clients-changed`, `ion:discovery`, and `ion:remote-relays-changed` reach both views. Studio's Devices section for a connection without `admin` (`environment.devices`, `auth.createOwnPairingLink`) is Studio-only: the phone's pairing controls call `auth.createPairingLink` and are denied without `admin`, and a person without it pairs their own devices from a desktop or web Studio. The relay configuration and the paired devices' secrets are read with `settings.load`, which returns them only to an `admin` connection. |
| Telemetry delivery health notifications (`installTelemetryHealthConsumer`) | Telemetry delivery on a server's Health page (state only, no notification) | The engine's `engine_telemetry_health` event drives an Electron `Notification` on the desktop. The phone shows each target's state on the Health page from `environment.systemMetrics.latest`'s `telemetryHealth`, read while the page is open. Rationale for no phone notification: telemetry delivery health is an operator concern the desktop alerts on locally; a push for it would need a doorbell kind of its own. |
| Health page (metrics, processes, host tools, telemetry, logs) | Connected-server load under the connection state, and a server's Health page | Studio watches with `environment.systemMetrics.watch` and renders `ion:system-metrics`. The phone's connection state shows CPU and memory from the `desktop_system_metrics` summary (`thinSummary`, `server/src/system-metrics/publisher.ts`), watched with `desktop_system_metrics_watch` while in the foreground. The phone's Health page reads `environment.systemMetrics.latest` (the full sample, per-process table included, and telemetry health) and `environment.systemMetrics.history` on a timer while it is on screen, `environment.host.toolchains` for host tools, and `environment.server.logTail` (`admin`) for logs. |
| Port Forward (the Ports canvas tab, and the Globe action on a conversation in another Environment; `desktop/src/main/connections/port-forward.ts`) | none | Desktop-only by design: it listens on the desktop's own loopback so a browser on that machine can reach a port on the Environment's host. A phone has no local browser workflow to serve. See [Port Forward](port-forward.md). |
| Studio Device Metrics and the idle-repaint warning (`desktop/src/main/device-metrics/`) | none | Desktop-only by design: they measure Studio's own Electron processes and never leave the device, so there is nothing for a phone to receive. |
| Composer draft (unsent prompt text) | Composer draft (`draftInputByTab`) | The server owns the draft: it lives on the conversation pane, is written to the tabs file, and is read back at boot, so an unsent prompt survives a quit. Studio's composer commits it debounced through the FORWARDED `setDraftInput` (`useComposerDraft.ts`); iOS commits it debounced through `desktop_set_draft` and reads the host's copy from `snapshot.ts` → `RemoteTabState.draftInput`. Adoption is on OPEN, never mid-edit: a client applies an incoming draft only to a conversation it is not focused on, so a push can never overwrite the words under the cursor. The consequence, and it is intended: text typed elsewhere while you sit on the same conversation appears when you leave and come back. |
| Composer extras (Input Bar `+` menu, Quick Tools and Project Quick Tools, `@file` mentions, prompt history, prompt stash, terminal and diff context chips, Composer Actions from the Studio SDK) | none | Desktop-only today. Each one shapes a prompt before it is sent; the resulting user turn and its attachments reach iOS unchanged through the existing echo and snapshot. Studio control resources (`ion-studio.*`) are deliberately kept off the mobile wire (`server/src/engine/event-wiring-mobile-filter.ts`). Rationale: the iOS composer is a separate, smaller surface, and these depend on a project checkout, a terminal, or a git panel that iOS does not have. |

## When to skip iOS

Only when the interface physically cannot work on iOS (e.g. a keyboard-only interaction, a desktop window management feature, or a rendering surface that doesn't exist on mobile). In that case:
- Note in the PR description why iOS was skipped.
- Consider whether an alternate mobile-appropriate rendering exists.
- At minimum, ensure the iOS app doesn't break or show stale data because of the desktop change.
